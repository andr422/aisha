# Контекст проекта (для Claude Code) — обновление 6 (20.08.2026)

## Что это
PWA для ежедневного сбора ABA-данных терапистами (русскоязычная ниша, аналоги
уровня TallyFlex). Три страницы:
- `final_fixed_aisha.html` — ежедневный сбор данных на занятии;
- `summary_fixed_aisha.html` — настройка протоколов/целей и профили детей;
- `abc.html` — ABC-запись поведения (эпизоды: время + A/B/C + длительность +
  интенсивность, ввод чипами).
Хостинг: GitHub Pages (репо andr422/aisha). Пользователь — не программист.

`index.html` — СТАРТОВАЯ страница (июль 2026, была голым списком из двух
ссылок): её ссылку кидают новичкам. Кнопка «Открыть приложение», первые три
шага, два правила (отправка данных; только инициалы), памятка,
установка на главный экран (Android/iPad), таблица «что где». Самодостаточна:
свои стили, шрифты из `fonts/`, никаких скриптов и service worker'а. Ссылку на
приложение НЕ менять на manifest start_url — это разные вещи (start_url ведёт
сразу в «Сбор», стартовая страница — на неё же кнопкой).

## Профили детей (реализованы; совместимость сверена — обновление 4)
Активен всегда ровно один ребёнок; его данные лежат под ПЛОСКИМИ рабочими
ключами (`protocol{i}_*`, счётчики, лог, `child_name`) — весь
код ввода их не различает. Переключение (только на сводной) сворачивает
рабочий набор текущего в `localStorage["aba_child_<id>"]` и разворачивает
выбранного. Список — `aba_children` [{id,label}], активный — `aba_active_child`.
История в IndexedDB — на ребёнка: ключ `aba_history::<id>`; первый профиль
наследует старую единую `aba_history`. При переключении с несданными
счётчиками — предупреждение, но переключение разрешено (данные остаются
в профиле неотправленными). Ежедневная показывает индикатор `#activeChild`
(«Ребёнок: <метка>») и берёт метку в отправку. ВЫВОД ПРОВЕРКИ: ежедневная
страница совместима со схемой профилей без префиксов — рабочие ключи плоские.

## Архитектура данных (ежедневная)
- История сессий: IndexedDB `aba_db` v2, стор `history`, ключ
  `aba_history::<activeChildId>`; кэш `historyCache`; фолбэк на localStorage
  (`window.__abaIdbFailed`); лимит 200 сессий; в таблице истории показываются
  последние 10. Раздел «История сессий» (#historyContainer) СКРЫТ по умолчанию,
  разворачивается пунктом меню «📋 История сессий» (historyVisible /
  setHistoryVisible / toggleHistoryFromMenu). Графики живут внутри этого
  раздела — при включении графиков история раскрывается автоматически.
- ИСТОРИЯ ПО ИМЕНИ ЦЕЛИ (с июля 2026): каждая сессия хранит `goalNames`
  (per-протокол массив имён целей, выровнен с data/promptDetails). Снятые с
  работы цели ОСТАЮТСЯ в истории (не теряются при смене набора). Хелперы
  goalValueAt/goalPromptAt/goalSeries (поиск по имени, позиционный фолбэк для
  старых сессий без goalNames), protocolGoalNames (текущие + исторические, без
  дублей). renderHistory/renderDaily/buildHistoryCsv/collectChartData — по
  имени. saveSelectedGoals БОЛЬШЕ НЕ мигрирует историю (migrateSessionData…
  удалена). Снятые цели в таблице помечены «(снята)». spliceHistoryProtocol
  режет и goalNames.
- ВЫРАВНИВАНИЕ ИСТОРИИ ПО НОМЕРУ ПРОТОКОЛА (июль 2026, по жалобе «процент
  прошлой сессии показывает не тот при переключении целей»). Две причины:
  (A) фолбэк в goalValueAt/goalPromptAt для СТАРЫХ сессий без goalNames брал
  getSelectedGoalIds (текущий выбор) → одна цель читала разные ячейки при
  выборе разных целей, процент «прыгал». Теперь фолбэк по existingGoalIds
  (стабильный порядок, legacyGoalPos) — значение не зависит от выбора.
  (B) finalizeSession раньше клал session.data/goalNames в порядке ОТРИСОВАННЫХ
  контейнеров, а читались они по НОМЕРУ протокола (session.data[i-1]). Если
  протокол пропущен (все цели на генерализации / ничего не выбрано), массивы
  сжимались и следующие протоколы читались со сдвигом. Теперь finalizeSession
  идёт по номерам 1..count и кладёт ПУСТОЙ срез [] для пропущенного протокола —
  session.data[i-1] всегда соответствует протоколу i. На сервер по-прежнему
  уходят только протоколы с собранными целями. Старые сессии в IndexedDB,
  записанные со сдвигом, задним числом не чинятся (для сессий без пропусков —
  а это большинство — всё совпадает).
- Очередь офлайн-отправки: стор `send_queue` (autoIncrement, FIFO); каждый
  запрос сначала в очередь, затем flushQueue(); авто-досыл по `online`,
  при старте, раз в 60 с; индикатор `#queueStatus`.
- Отправка: ТОЛЬКО итоги сессии по кнопке (SESSION_ENDPOINT). С июля 2026 —
  ЧЕСТНОЕ ПОДТВЕРЖДЕНИЕ ДОСТАВКИ (no-cors убран): sendPacket шлёт обычный
  CORS-запрос с Content-Type text/plain (JSON в теле; text/plain — чтобы не
  было preflight, который Apps Script не умеет; redirect: follow), читает
  ответ; доставлено = {ok:true} (или «OK» от старой версии скрипта). Отказ
  сервера → item.attempts++ (queuePut), пакет НЕ блокирует FIFO; после
  STUCK_ATTEMPTS=30 пропускается, индикатор «⚠ Не доставлено: N. Нажмите —
  повторить» (клик сбрасывает attempts). Сетевая ошибка → стоп до следующего
  flush. Отправка отдельных кликов УДАЛЕНА (июль 2026) — последовательность
  ответов уходит внутри итогов (`responses`).
- ЗАЩИТА ОТ ДУБЛИКАТОВ (июль 2026): каждому пакету при постановке в очередь
  присваивается `uid` (packetUid(), один раз — при повторах НЕ меняется).
  Скрипт помнит 300 последних uid (Script Properties `_uids`) и на повтор
  отвечает {ok:true,duplicate:true} без записи. Номер запоминается ТОЛЬКО
  после успешной записи, поэтому реальная ошибка по-прежнему приводит к
  повтору. Зачем: Apps Script с заметной частотой (~1 из 3) возвращает
  ПУСТОЙ ответ, хотя запись прошла — без uid повтор создавал бы дубль строки.
  Пакеты без uid (старая версия приложения) обрабатываются как раньше. Скрипт-приёмник (Apps Script) сам
  раскладывает данные по таблицам детей: «ABA — <метка>» в папке «ABA — дети»
  на Диске владельца, по полю `child` пакета. Поэтому МЕТКИ ДЕТЕЙ НЕ
  ПЕРЕИМЕНОВЫВАТЬ без нужды (новая метка = новая таблица). Правки скрипта
  разворачивать ТОЛЬКО через «Управление развёртываниями → Новая версия»
  (не «Новое развёртывание» — иначе сменится URL).
- РЕЖИМ БЕЗ ОЧЕРЕДИ (июль 2026, найдено по жалобе «с айфона в Chrome не
  отправляет»): если IndexedDB недоступна (`window.__abaIdbFailed` — приватный
  режим, урезанное хранилище браузера), queueAdd шлёт пакет НАПРЯМУЮ через
  sendDirect(), который БРОСАЕТ ошибку при недоставке. Раньше ошибка глушилась
  console.error'ом, очередь была пуста, и приложение рапортовало «Готово,
  отправлено», хотя в таблицу ничего не ушло. Теперь: на ежедневной отказ
  доходит до confirmFinalize → тост с причиной, счётчики НЕ обнуляются, сессия
  НЕ уходит в историю (можно повторить); на ABC и «Частоте» запись остаётся в
  локальном журнале с честным тостом «сохранено на планшете, но в таблицу не
  ушло». Индикатор `#queueStatus` в этом режиме сразу пишет «⚠ Этот браузер не
  хранит очередь — отправляйте только при интернете». Одинаково на трёх
  страницах (у каждой свои копии queueAdd/sendPacket).
- СЛЕПАЯ ОТПРАВКА (июль 2026, из-за Chrome на iPhone). Диагноз: адрес скрипта
  в Chrome открывается, из Safari и с домашнего экрана всё уходит, а fetch со
  страницы падает с «TypeError: Load failed» — браузер обрывает запрос, ответ
  прочитать нельзя. Решение: если ОБЫЧНЫЙ запрос бросил ошибку, flushQueue
  повторяет тот же пакет через sendBlind() — `mode:"no-cors"`, ответ не
  читается. Успех no-cors означает только «ушло с телефона», поэтому пакет НЕ
  удаляется: ему ставится `blindSent` (метка времени), автоповторы его
  пропускают, а индикатор пишет «📨 Ушло без подтверждения: N. Проверьте
  таблицу и нажмите». Тап на ежедневной: «да, записи в таблице» → удалить из
  очереди; «нет» → снять `blindSent` и попробовать обычным путём снова. На ABC
  и «Частоте» — тот же sendBlind и та же пометка, но разбор только на «Сборе»
  (очередь общая: одна IndexedDB `aba_db`, стор send_queue). Дубликатов слепая
  отправка не создаёт — работает uid-дедупликация в Apps Script.
  ВАЖНО: у каждого браузера на iOS СВОЁ хранилище — очередь из Chrome не видна
  ни Safari, ни приложению с домашнего экрана.
- Счётчики текущей сессии: `aba_counts_v2` (по классам кнопок, объект
  {s,p,e} на блок) с авто-миграцией из старого позиционного `aba_counts`.
- `aba_response_log`, `aba_prompt_details` — в localStorage, по индексам блоков.
- При смене выбранных целей несданные счётчики/лог/подсказки мигрируют по
  именам целей (snapshotInProgressData/restoreInProgressData), undo-стек
  очищается; история мигрирует по именам (migrateSessionDataForProtocol).
- ПРИВЯЗКА СЧЁТЧИКОВ К ЦЕЛЯМ (июль 2026, по жалобе «нажимались кнопки и
  собиралось не то»). `aba_counts_v2`, `aba_prompt_details`, `aba_response_log`
  — массивы ПО ПОРЯДКУ блоков. Раньше это защищалось только вокруг «Выбрать
  цели»; любое другое изменение набора (правка/удаление цели на «Настройке»,
  новый протокол) сдвигало массивы, и несданные числа оказывались на ЧУЖИХ
  целях — выглядело как «кнопки нажимались сами». Теперь saveProgress рядом
  пишет `aba_block_keys` = массив ключей «протокол||имя цели», а renderDaily в
  начале зовёт realignProgressToBlocks(): если расклад изменился, счётчики,
  подсказки и лог перекладываются по ключам, новые цели получают нули, а по
  исчезнувшим целям с ненулевыми данными выводится честный тост «их несданные
  данные пропали: …». Вызов строго ДО normalize*Length (иначе хвост массивов
  обрежется). Ключ `aba_block_keys` добавлен в isChildDataKey на сводной и
  стирается вместе со счётчиками при удалении протокола (там номера протоколов
  перенумеровываются, старые ключи невалидны — это же предупреждение есть в
  confirm перед удалением).
  ЦЕЛИ-ТЁЗКИ: у повторяющихся названий к ключу добавляется «||#N» (у первого
  вхождения — нет, ради совместимости). Без этого две цели с одним названием
  получали одни и те же числа. Теми же ключами пользуются snapshot/
  restoreInProgressData — раньше у них был тот же дефект.
  ЦЕЛЬ С НЕСДАННЫМИ ДАННЫМИ НЕ ПРЯЧЕТСЯ: renderDaily фильтрует освоенные цели
  через hasUnsentData(unsentCountsByKey(), …) — если по цели уже есть нажатия,
  она остаётся на экране, даже когда ей проставили дату освоения; уйдёт на
  генерализацию после отправки, когда счётчики обнулятся.

## Действия с целью и отмена (июль 2026)
- «Выбрать цели» — теперь класс `.select-goals` (мелкая, без заливки, серая) и
  показывается ТОЛЬКО у раскрытого протокола (CSS `.collapsed .select-goals`).
  Вместе с ней в свёрнутом виде прячется и кнопка PDF.
- ДОЛГОЕ НАЖАТИЕ (450 мс, как у «P») по `.goal-label` открывает строку
  `.goal-actions` с кнопками «Очистить» / «Отмена» (wireGoalLongPress).
  clearGoalCounts(block) обнуляет счётчики ЭТОЙ цели, её разбивку подсказок и
  лог ответов, выкидывает её нажатия из undoStack и пишет тост. Обычный тап по
  названию не делает ничего; выделение текста и меню iOS на `.goal-label`
  отключены (user-select/touch-callout/contextmenu).
- ОТМЕНА не ограничена по времени: `undoStack` живёт в ПАМЯТИ страницы, значит
  отменять можно сколько угодно нажатий подряд, но всё теряется при
  перезагрузке/переходе на другую вкладку (счётчики при этом сохраняются) и
  очищается при отправке, смене набора целей и очистке цели. Всплывающая
  плашка `#undo-banner` прячется через 5 с ТОЛЬКО если стек пуст; постоянная
  кнопка `#undoBtn` в шапке доступна всегда.

## Свёрнутые протоколы на «Сборе» (июль 2026)
Протокол на ежедневной по умолчанию СВЁРНУТ: в шапке только название, каретка
и подпись «N целей · нажмите, чтобы открыть» (или «· собрано по N»). Цели с
кнопками лежат в `.proto-goals` внутри `.protocol-container`; свёрнутое
состояние — класс `collapsed` на контейнере, CSS прячет `.proto-goals`.
Тур на «Сборе» объясняет это шагом «Протоколы свёрнуты» (until:
`.protocol-container:not(.collapsed)` — если всё свёрнуто, ждёт настоящего
нажатия) и следом шагом про «Выбрать цели».
Нажатие на название (`.proto-toggle`) переключает и запоминает состояние в
`protocol{i}_open` = "1"/"0" (ключ подходит под /^protocol\d+_/, поэтому сам
ездит с ребёнком и переживает перенумерацию при удалении протокола).
ИСКЛЮЧЕНИЕ: протокол с несданными нажатиями раскрывается ВСЕГДА (проверка
hasUnsentData) — начатую работу прятать нельзя, даже если её свернули руками.
В режиме «по одной» сворачивание игнорируется (CSS body.single-mode). Подпись
пересчитывается в updateProtocolSummaries() — зовётся из renderDaily и из
updatePercentages (то есть после каждого нажатия). Тур на «Сборе» перед шагом
про кнопки раскрывает первый свёрнутый протокол (before), VERSIONS.final = 3.

## ABC-запись (abc.html)
- Эпизод: время (input time, авто «сейчас») + чипы A, B, C — порядок на
  экране именно A → B → C (июль 2026), заголовок B выделен классом
  `.section-label.main`, он же единственное обязательное поле;
  МНОЖЕСТВЕННЫЙ выбор (renderChipGroup(..., multi=true), selected[group] —
  массив; в запись склеиваются через ", "); «✎ вписать» — ПЕРВЫЙ чип группы,
  свой текст через prompt (один кастомный на группу). Длительность
  (5 пресетов) и интенсивность — шкалы, выбор ОДИНОЧНЫЙ.
- Списки A/B/C настраиваются на самой странице («⚙ Списки», textarea по
  строке на вариант), ключи abc_antecedents/abc_behaviors/abc_consequences;
  пустой список = дефолты. Журнал: abc_log (localStorage, лимит 500,
  показываются последние 30, удаление ✕ — только локально).
- ВСЕ ключи abc_* входят в рабочий набор ребёнка (isChildDataKey на сводной:
  /^abc_/) — списки и журнал у каждого ребёнка свои.
- Отправка: сразу при записи эпизода, через ту же очередь send_queue на
  SESSION_ENDPOINT с payload {type:"abc", child, date, time, behavior,
  antecedent, consequence, duration, intensity}. Скрипт-приёмник различает
  пакеты по type и пишет эпизоды на лист «ABC» таблицы ребёнка.
- Экспорт журнала в CSV — кнопка на странице.

Списки по умолчанию (DEFAULT_A/B/C) — только ЗАГОТОВКА: они подставляются,
пока терапист не правил списки через «⋮ → Списки». Если правил, его версия
лежит в `abc_*` и defaults игнорируются, поэтому правка кода НЕ меняет списки
на планшетах, где их настраивали (18.08.2026: «Агрессия к другим» →
«Бьёт рукой», «Самоагрессия» → «Бьёт себя по голове» — на настроенных
планшетах менять руками). Списки поведений СВОИ У КАЖДОГО РЕБЁНКА.

## Частота поведения (frequency.html)
- Счётчики проявлений: карточка на поведение, большая «+», мелкая «−».
  «Раз в час» с экрана тераписта убрано 20.08.2026 (решение пользователя):
  не показывается ни в карточке поведения, ни в журнале, ни на графике —
  у графика осталась одна шкала «количество». Само значение СЧИТАЕТСЯ и
  уходит в журнал, в CSV, в таблицу и на сервер, а видно его в кабинете
  супервизора. Причина: на наблюдении в 1–3 минуты пересчёт в час даёт
  «180 раз в час» на трёх проявлениях и пугает, а решение по нему принимает
  супервизор.
  Список поведений СВОЙ (ключ `freq_behaviors`, с 20.08.2026; раньше был
  общий с ABC). При первом открытии после обновления список один раз
  переносится из `abc_behaviors`, чтобы настроенные поведения не пропали
  (`splitBehaviorsOnce`, отметка `freq_behaviors_split`). Оба ключа
  начинаются с `freq_`, поэтому едут вместе с ребёнком и попадают в копию.
  СТАРОЕ (не действует): список поведений ОБЩИЙ с ABC — правится на любой из
  двух страниц.
- Таймер наблюдения по метке времени (`freq_start`) — переживает перезагрузку;
  «▶ Начать / ⏹ Остановить». Частота в час = count / минуты * 60, показывается
  под именем поведения и пишется в запись. Без таймера считать можно, но
  раз/час будет пусто.
- Ключи (в рабочем наборе ребёнка, /^freq_/): `freq_counts` (текущее
  наблюдение {поведение:число}), `freq_start`, `freq_log` (журнал, лимит 300,
  на экране последние 20).

## Подпись-тренд (goalTrendStatus, 17.08.2026)
Чистая статистика на клиенте, без сети и AI: описывает, что видно в процентах,
и НИЧЕГО не советует. Пороги — именованные константы в начале функции:
`TREND_MIN_POINTS` 4, `TREND_PLATEAU_SPREAD` 10 п.п., `TREND_PLATEAU_MEAN_MAX`
80, `TREND_GROWTH_DELTA` 15 п.п., `TREND_SWING_SPREAD` 50 п.п. Окно — последние
10 сессий, то же, что у спарклайна.
Три статуса: плато (хвост в узком коридоре, среднее ниже критерия; длина
считается `plateauRun`), рост (среднее второй половины окна выше первой И
«ступенька»: худший результат второй половины не ниже лучшего из первой —
без этого качели `10,90,20,85,15,80` выдавались за рост), разброс.
ПРЕДОХРАНИТЕЛЬ: ряд только из 0 и 100 глушит рост и разброс — в реальных
данных три четверти замеров сделаны ПО ОДНОЙ ПРОБЕ, и такой ряд означает
разрешение данных, а не качели. Плато он не трогает.
ГДЕ ПОКАЗЫВАЕТСЯ: только в отчёте (столбец «Динамика», формулировки мягче:
«без изменений · N сессий», «растёт», «неровно», прочерк). На «Сборе»
сознательно НЕ показывается — там терапист работает, а не разбирает данные.

## Подсказки на экране — тур (tour.js)
Общий модуль, подключается ПОСЛЕ tabbar.js на 4 страницах (сбор, сводная, ABC,
частота). Затемняет экран, подсвечивает элемент («прожектор» = прозрачный div
с box-shadow 0 0 0 9999px) и показывает карточку с пояснением, счётчиком шагов
и кнопками «Закрыть» / «Дальше». Сценарии — объект SCRIPTS по страницам
(pageId() определяет страницу по имени файла); шаг = {sel, title, text,
until, doText, empty, before, after}.

Пустой планшет (ни протоколов, ни целей) — штатный случай, ради него два
режима:
- `until` — селектор результата шага. Если результата ещё НЕТ, шаг ждёт, пока
  терапист сам нажмёт подсвеченную кнопку: показывает строку-задание `doText`,
  «Дальше» превращается в «Пропустить», появление результата ловят
  MutationObserver + опрос раз в 400 мс (watchFor). Если результат уже есть —
  обычный рассказывающий шаг. Так сводная ведёт новичка: добавить протокол →
  назвать → добавить цель → сформулировать.
- `empty: {title, text}` — что показать, если элемента нет и создавать его тут
  нечем: карточка по центру без подсветки (на «Сборе» — «здесь появятся кнопки
  оценки, сначала заведите протокол»). Шаг без `until` и без `empty`, элемента
  которого нет, по-прежнему пропускается.

Шаг открывается ОТЛОЖЕННО (setTimeout 0, функция openStep): клик по «Дальше»
ещё всплывает к document, где обработчик «клик мимо меню» закрыл бы меню,
которое шаг только что открыл через before: openMenu. Без этой отсрочки шаги
про меню подсвечивали уже закрытое меню.

ПУСТАЯ КАРТОЧКА, КОТОРАЯ НЕ ЗАКРЫВАЕТСЯ (июль 2026, по жалобе «если у ребёнка
активна генерализация»). Причина: шаг про блок #genBox прокручивает страницу
вниз, а меню «⋮» живёт в шапке — его выпадашка position:fixed позиционируется
от кнопки (`drop.style.top = r.bottom + 6`). Когда кнопка ушла выше экрана
(замер: top −1008), выпадашка получала top −966, и карточка подсказки
(`top = r.bottom + 14`) уезжала в отрицательные координаты — терапист видел
затемнение с подсветкой у верхнего края и НИ карточки, ни кнопки «Закрыть».
Две правки: (1) openMenu делает window.scrollTo(0, 0) ПЕРЕД открытием — меню
всегда на экране; (2) в render() позиция карточки жёстко зажимается в границы
экрана: `top = Math.max(8, Math.min(top, vh - ch - 8))`, а vw/vh берутся с
фолбэком (в некоторых обёртках innerHeight = 0, и без него карточка тоже
уезжала бы в минус).

Видимость элемента определяется через getClientRects(), НЕ через ширину:
у блочных элементов она бывает 0 в момент перестроения раскладки.
Запуск: автоматически при первом открытии страницы И ещё раз после обновления
подсказок. `aba_tour_seen` = {page: НОМЕР ВЕРСИИ} (старое значение `true`
читается как версия 1). Рядом со SCRIPTS лежит объект VERSIONS — номер на
страницу; ПОДНИМАЙТЕ номер страницы, шаги которой правите, тогда тур один раз
всплывёт у всех, кто его уже видел. Чужие номера не трогать — иначе людям
заново покажут то, что не менялось. При таком повторном показе на ПЕРВОЙ
карточке видна пометка `.aba-tour-new` («Подсказки обновились»); при ручном
запуске из меню её нет (isUpdate сбрасывается). Текст шага пишется в
`.aba-tour-text`, НЕ в первый `<p>` — выше него лежит эта пометка.
Вручную — пункт меню «💡 Подсказки на экране» (id="tourBtn",
обработчик вешает сам tour.js). guide.html остаётся как текстовый справочник
(печать/отправка новичку заранее).

## Холодные пробы (июль 2026)
Протокол можно пометить как «холодную пробу» — навык проверяют ОДИН раз за
занятие, до обучения. Галочка на сводной под названием протокола
(`.cold-row` / `input.cold-probe`), ключ `protocol{i}_coldProbe` = "1" (под
шаблон /^protocol\d+_/ — едет с ребёнком и переживает перенумерацию при
удалении протокола; сохраняется в bindEvents по классу, у чекбокса нет value).
На ежедневной блок такой цели получает класс `cold-probe` и подпись
`.cold-note`. applyColdProbeLocks() считает сумму трёх счётчиков блока: как
только она > 0 — всем трём кнопкам ставится disabled, блоку класс `cold-done`,
подпись меняется на «проба записана». Разблокировка: «Отменить действие»,
очистка цели долгим нажатием, отправка занятия (счётчики обнуляются). Вызовы:
в конце updatePercentages (туда сходятся нажатие/отмена/очистка/loadProgress) и
в конце renderDaily (блоки пересобраны). startPress у кнопки «P» проверяет
btn.disabled, иначе долгое удержание открывало бы модалку на закрытой кнопке.

## Генерализация освоенных целей (июль 2026)
Освоенная цель (есть `_masteryDate`) УХОДИТ из ежедневного списка: renderDaily
фильтрует её через isGeneralizing() и пропускает протокол, у которого не
осталось видимых целей. Вместо неё — блок `#genBox` под списком: свёрнут по
умолчанию (`aba_gen_open`), в шапке «Генерализация · N целей» и общий счёт.

Модель: 3 категории (стимулы/места/люди) × 3 условия = 9 проб на цель.
- ПЛАН — существующие поля сводной `_genStim` / `_genPlace` / `_genPeople`:
  теперь это списки через запятую, из них берутся подписи кнопок; не заполнено
  — «1 / 2 / 3».
- ФАКТ — `protocol{i}_goal{j}_genLog` = `{stim:[дата|null ×3], place, people}`.
  Тап = успешная проба (системная дата), повторный тап снимает.
- 9 из 9 → пишется `_genDoneDate`, строка показывает «✓ обобщено»; если отметку
  сняли, дата удаляется.
- ПРОТОКОЛ, УШЕДШИЙ ЦЕЛИКОМ (июль 2026, по жалобе «в таблицу пришёл только
  один протокол»): если ВСЕ цели протокола на генерализации, протокол вообще не
  рисуется на «Сборе» — значит и пакета по нему не будет, в таблице за этот день
  пусто. Раньше это происходило молча. Теперь renderDaily копит hiddenProtocols
  и печатает под списком заметную плашку `.hidden-protocols`: «Не показаны на
  занятии: …» + кнопка «Вернуть в занятие» (ставит `_keepDaily` всем целям на
  генерализации, через snapshot/restoreInProgressData). Плюс окно подтверждения
  отправки перечисляет протоколы поимённо («Протоколов: 4 — Имитация, …»), чтобы
  недостачу было видно ДО отправки.
- Кнопка в строке двусторонняя: `_keepDaily` = "1" возвращает цель в ежедневный
  сбор (дата освоения сохраняется), повторное нажатие убирает. В блоке видны
  ВСЕ освоенные цели, в том числе возвращённые.
- Переключение перестраивает список блоков, поэтому идёт через
  snapshotInProgressData / restoreInProgressData (как «Выбрать цели»), иначе
  несданные счётчики съедут на соседние цели.
Все ключи попадают под `/^protocol\d+_/` в isChildDataKey — правок не
потребовалось. В отчёте для родителей — раздел «Перенос навыков в жизнь».

ОТПРАВКА В ТАБЛИЦУ: пакет `{type:"gen", child, date, items:[{protocol, goal,
category, condition, mark, date, progress}]}` уходит ВМЕСТЕ с итогами занятия
(в finalizeSession, той же кнопкой — отдельных «кликов в сеть» в приложении
по-прежнему нет). Скрипт пишет строку на пробу на лист «Генерализация».
Чтобы повторные отправки не плодили строки, у каждой цели есть зеркало
`_genSent` (та же форма, что и `_genLog`): collectGenRows() отдаёт только
РАЗНИЦУ (`mark` = «проба пройдена» / «отметка снята»), markGenSent()
переписывает зеркало ПОСЛЕ того, как пакет лёг в очередь. Число проб к
отправке показывается в окне подтверждения.

## Автодата введения цели
markIntroDate(block) вызывается из increment() — единственной воронки всех
нажатий (−, короткая P, тип подсказки из модалки, +). При ПЕРВОМ нажатии по

(`introSet`), и undoLastAction снимает дату, если отменяют то самое нажатие,
которым цель завелась (иначе промах оставил бы дату). Ключ уже был в
isChildDataKey (шаблон `/^protocol\d+_/`), отдельной правки не потребовалось.

## Автодата освоения
markMasteredGoals() вызывается в finalizeSession() ПОСЛЕ setHistory: для каждой
существующей цели считает checkMastery(goalSeries(i, name, history.slice(-3))) —
тот же критерий, что и бейдж «освоено» на карточке. Если критерий выполнен, а
`protocol{i}_goal{j}_masteryDate` ПУСТ, пишет туда дату ЭТОГО занятия
(getSessionDateForServer() — СИСТЕМНАЯ дата, формат YYYY-MM-DD).
Уже заполненную дату не трогает (ручной ввод тераписта в приоритете), повторные
занятия дату не сдвигают. finalizeSession возвращает список отмеченных целей;
confirmFinalize показывает по нему отдельный тост через 3.2 с после основного.

## Дата занятия (июль 2026: поле убрано)
Поле «Дата сессии» на сводной УДАЛЕНО. Дата берётся из системных часов в момент
отправки: getSessionDateForHistory() → дд.мм.гггг (история/таблица),
getSessionDateForServer() → гггг-мм-дд (поля даты, автодата освоения). Обе
считают по ЛОКАЛЬНОМУ времени (toISOString() дал бы вчерашний день поздно
вечером). Ключ `session_date` больше не пишется, но оставлен в isChildDataKey /
isSettingKey, чтобы старые значения корректно сворачивались и удалялись.
Следствие: внести занятие ЗАДНИМ ЧИСЛОМ через приложение нельзя — правка
только в таблице вручную. Окно подтверждения отправки показывает дату
(«Ребёнок: … Дата: …») — это информирование, а не поле для правки.

## Свой сервер и двойная запись (август 2026)
`SERVER_ENDPOINT` в final/abc/frequency рядом с `SESSION_ENDPOINT`:
`https://api.abachecklist.ru/api/ingest?k=<ключ>`. Пустая строка выключает
сервер. `queueAdd` кладёт ОБЕ копии пакета одной транзакцией IndexedDB под
ОДНИМ `uid` (`packetTargets(item)` = [item.endpoint, SERVER_ENDPOINT]);
`sendDirect` (режим без IndexedDB) считается успешным, если принял ХОТЯ БЫ
ОДИН адрес. В `flushQueue` сетевой сбой больше НЕ делает `break` (иначе
лежачий сервер заблокировал бы доставку в таблицу) — недоступный адрес
попадает в `deadEndpoints` и пропускается только он.
Ключ лежит в коде клиента, то есть виден с планшета: это защита от случайных
запросов из интернета, а не от человека. Снимется на шаге «вход по логину».

СЕРВЕР: Ubuntu 26.04 на Timeweb (201.34.132.223), PocketBase 0.39 на
127.0.0.1:8090, наружу через Caddy (сертификат Let's Encrypt сам). Приёмник —
`pb_hooks/ingest.pb.js`, принимает ТОТ ЖЕ формат, что Apps Script; защита от
дублей по `uid` через UNIQUE-индекс в `packets`. Админка
`https://api.abachecklist.ru/_/`. Бэкапы ночью в S3 Timeweb (восстановление ни
разу не проверяли — это открытый пункт). Исходники сервера — в
`server/` рядом с приложением.

ЛОВУШКИ ДАННЫХ (аудит 18.08.2026, учитывать при кабинете супервизора):
- Числовые поля PocketBase НЕ хранят пустоту, туда ложится 0. Так «цель не
  отрабатывали» становилась 0% — починено флагом `no_data`; частота без
  таймера становилась «0 раз в час» — различитель `minutes = 0`, срез
  `v_frequency` отдаёт по таким строкам пустоту. ЛЮБОЕ новое числовое поле
  проверять на этот же случай.
- «—» из приложения (не выбрано) писалось как значение — теперь нормализуется
  в пустоту на приёме.
- Одинаковые названия целей живут в РАЗНЫХ протоколах — группировать только по
  паре «протокол + цель».
- Занятие ищется по паре «ребёнок + дата»: один ребёнок за день у двух
  терапистов сольётся в одно занятие. Чинить вместе с логинами.
- ОТСУТСТВИЕ строки ≠ ноль: невыбранные цели не отправляются вовсе.

Вторичные действия скрыты в меню «⋮ Меню» (wireMenu, как на ежедневной:
позиционирование с прижимом к краям, закрытие по клику мимо/Esc). Пункты
(id сохранены, обработчики в bindToolbar/wireTemplates/wireBackup): экспорт
настроек, импорт настроек, шаблоны протоколов, бэкап планшета.

## Полный бэкап планшета (сводная, «🗄 Бэкап планшета»)
Отдельно от per-child экспорта настроек. backupDevice: весь localStorage +
весь стор history IndexedDB (история aba_history::<id> всех детей + PDF-блобы
aba_pdf::*, блобы → dataURL). Очередь send_queue НЕ включается (временное
состояние доставки). Файл `aba_backup_<дата>.json`, _type:"aba_backup".
restoreDevice — ПОЛНАЯ замена (localStorage.clear + очистка/перезапись стора
history одной транзакцией) с жёстким confirm, затем reload. Проверка _type.

## Известные ограничения / планы
- Старое развёртывание скрипта итогов (`AKfycbx1ZyMrh…`, пишет в архивную
  таблицу Aisha) держится до обновления всех планшетов, потом архивировать.
- Меню «⋮» справа в шапке ежедневной (menu-wrap/wireMenu): «Вид: список/по
  одной» (#viewModeBtn живёт в меню), «📊 Графики», «⬇ Экспорт (CSV)»,
  «⬇ Отчёт с графиками». «Отменить действие» и «Отправить данные» — вне меню
  (нужны мгновенно). Закрытие: клик мимо, Esc, после любого пункта.
- Экспорт истории замеров: пункты меню «⋮».
  «⬇ Экспорт (CSV)» — вся история активного ребёнка (до 200 сессий) в длинном
  формате «Дата;Протокол;Цель;Процент;Подсказки», UTF-8 с BOM, разделитель
  «;» (для русского Excel), пустые замеры пропускаются. «⬇ Отчёт с графиками» —
  самодостаточный HTML-файл для родителей/супервизора (SVG-графики по целям,
  buildReportHtml). Кнопка «📊 Графики» — раздел графиков прямо в приложении
  (renderCharts). Общая основа: collectChartData + buildChartSvg (шкала
  0–100, пунктирные пороги 80/50, цвета точек как у спарклайна).
- ОТКРЫТО на 18.08.2026: вход по логину (автор у занятия, снимает ключ из кода
  клиента); синхронизация вниз (планшет получает только своих детей); кабинет
  супервизора; отключение Google-таблиц; проверка восстановления из бэкапа;
  переезд приложения на свой домен (у планшетов данные привязаны к origin —
  нужен план с бэкапами); переименование файлов без «aisha» (ломает ярлыки на
  домашних экранах — только через страницы-редиректы); решить судьбу режима
  «по одной цели» (спросить терапистов, пользуется ли им кто-нибудь).
- Рынок и позиционирование — отдельный файл COMPETITORS.md. Коротко: ниша НЕ
  пуста (ABAdata.ru, AbaDataPro), якорь цены ~1000 ₽/мес за специалиста,
  выигрываем не широтой функций, а надёжностью основного сценария сбора.
  Решено НЕ делать: модель Хенли, биллинг/супервизию/контракты, AI-советы
  «что делать дальше» (граница ответственности специалиста).

## Стиль работы
Пользователь общается по-русски; комментарии в коде по-русски. Перед крупными
переделками — обсуждать варианты (пользователь любит выбирать по макетам).
Точечные правки предпочтительнее рефакторинга. После правок ежедневной —
всегда напоминать про версию sw.js и предупреждение тераписту, если меняется
моторика ввода.

## Страницы показа (папка demo/, 20.08.2026)

Сделаны для показа руководству центра, к работе терапистов отношения не имеют
и из вкладок приложения не доступны. Адрес: `<сайт>/demo/`.

- `index.html` — вход по логину, МАКЕТ (проверки пароля нет и быть не может:
  страница статическая). Три роли ведут на нужные страницы.
- `therapist.html` — настоящее приложение в рамке телефона (iframe на
  `../final_fixed_aisha.html?notour=1`, экран ровно 390×750, переключатель
  «телефон / планшет»). Подсказки внутри рамки выключены параметром
  `notour=1` — его понимает `tour.js`. Если на устройстве нет протоколов,
  страница предлагает завести ДЕМО-ребёнка с двумя протоколами (кнопка
  появляется ТОЛЬКО на пустом устройстве и данные детей не трогает; ключ
  `demo_seeded`, рядом кнопка «убрать»).
- `supervisor.html` — кабинет: сводка по центру, карточки детей с сигналами,
  карточка ребёнка (цели, проценты, спарклайны, статусы, поведение, ABC).
  Два уровня, как на «Настройке» в приложении: сначала протоколы (в шапке —
  сколько целей, сколько освоено, среднее по протоколу), первый раскрыт;
  внутри цели, каждая раскрывается в свою историю — большой график по всем
  датам (`chart()` в demo.js) и таблица КАЖДОГО замера с журналом ответов.
  Отдельная карточка «История занятий» — по дням, тоже с раскрытием.
  Карточка «Общие сведения» считает восемь правил (20.08.2026):
  нет данных ≥5 дней · на последнем занятии у половины целей ≤2 проб
  (процент бинарный) · 3 замера подряд ≤30% · при 3+ занятиях цель собрана
  один раз · один и тот же антецедент не меньше чем в половине эпизодов
  (от 3 эпизодов) · плато · критерий освоения · «ничего срочного».
  Формулировки — ФАКТ из данных, без назначения вмешательства: что делать
  с целью, решает супервизор (решение пользователя 20.08.2026). Повторы
  сворачиваются в одну строку с тремя именами и «и ещё N».
  Последняя строка — общая сводка по ребёнку (`summaryLine`): ярлык
  («идёт хорошо» / «в целом ровно» / «есть на что посмотреть» / «данные не
  поступают» / «данных пока нет») плюс фраза о целях, фраза о частоте, фраза
  об эпизодах ABC и оговорка о надёжности («в N% замеров одна-две пробы»).
  Частота и ABC считаются РАЗДЕЛЬНО и не складываются: одно поведение может
  попасть и в счётчик наблюдения, и в эпизод. Про ABC говорим «участились»
  только если истории не меньше 28 дней — иначе «3 против 0» у только что
  заведённого ребёнка означало бы «раньше не записывали», а не рост.
  Оговорка обязательна: на одиночной пробе процент бинарный, и без неё
  сводка выглядела бы увереннее, чем данные позволяют.
  Ниже во всю ширину — «Поведение: как часто»: многолинейный график
  (`multiChart` + `behaviorSeries` в demo.js), переключатель «раз в час /
  сколько раз», кликабельная легенда и таблица наблюдений. Если ни в одном
  наблюдении не было таймера, шкала «раз в час» пуста — страница сама
  показывает количество и объясняет почему. Внизу во всю ширину — «Эпизоды ABC»: дата, время,
  интенсивность, длительность и три части (до / что произошло / после).
- `feed.html` — лента поступлений, сама обновляется раз в 10 с; новая строка
  подсвечивается. Этим доказывается «данные уходят и их видно».
- `center.html` — специалисты и распределение, МАКЕТ (на сервере нет ни входа,
  ни связи «терапист ↔ ребёнок»); дети и их числа настоящие.
- `scenario.html` — шпаргалка выступающему.
- `demo.js` — загрузка и разбор; статусы целей считаются по ТЕМ ЖЕ правилам,
  что в отчёте (освоено = 3 замера ≥80; плато = 4 замера, разброс <10, среднее
  <80; рост = ступенчатый подъём ≥15; ряды из одних 0/100 — без ярлыка).

**Данные настоящие**, читаются с сервера: хук `pb_hooks/demo_read.pb.js`,
`GET /api/demo?k=<ABA_DEMO_KEY>`, только чтение, ключ ОТДЕЛЬНЫЙ от приёмника
(`/etc/systemd/system/pocketbase.service.d/demo.conf`). Отдаёт метки детей,
замеры, ленту пакетов, счётчики поведения и ЭПИЗОДЫ ABC ЦЕЛИКОМ (20.08.2026,
по просьбе пользователя: супервизор должен их читать). Заметки не отдаёт.
Тексты ABC — самое чувствительное здесь: в «до/после» бывает описание
ситуации в семье, а ключ лежит в открытом коде страницы. Тем важнее выключить
эндпоинт сразу после показа.
**Выключить после показа:** удалить `demo_read.pb.js` на сервере и
`systemctl restart pocketbase` — приём данных с планшетов это не затрагивает.

Кэш: `sw.js` намеренно пропускает всё, что в пути содержит `/demo/`, — иначе
страницы показа отдавали бы старую копию вместо живых данных.
